# 存量记录批量补字段：匹配键选错 = 静默伪造

Realized 2026-08-23 给 dashboard 历史观点批量补深度摘要时，**我自己写的回填脚本**造成的。
这是本类任务里最危险的失败模式：不报错、日志好看、数据进库、没人发现。

适用场景：给**已有的历史记录**批量补一个新字段（摘要 / 翻译 / 分类 / 标签 / 富化描述），
数据由 LLM 或子 agent 产出后再写回原表。

---

## 事故经过（照抄，因为这个坑很容易重犯）

数据结构：
- 聚合层 `history()` 会把**连续多天内容相同**的记录合并成区间 `(first_date, last_date)`
- 底层实际按天存成 `daily/YYYY-MM-DD.json`

子 agent 拿到的是**区间的 last_date**，要写回的是**按天的文件**。于是我想：
「按 `(实体, 日期就近)` 回溯——找 last_date ≥ 本文件日期的最近一条」。

结果：

```
输入 1188 条  →  回填 2160 条
```

我一开始还觉得是区间覆盖的正常放大。**实测校验后发现 972 条被贴上了完全不同观点的摘要**
（2025-12-18 的观点挂上了 2026-04-08 的分析）。

**这是伪造。** 而且：
- 总量守恒 ✅
- 脚本零报错 ✅
- 日志显示「回填成功 2160 条」，比预期还多，**看起来像超额完成** ✅

---

## 正解：用内容当匹配键，日期只做辅助校验

```python
# ✅ 只按 (实体, 正文全文) 精确匹配
idx = {}
for r in rows:
    k, det, cmt = r.get("kol"), r.get("detail"), (r.get("comments") or "").strip()
    if k and det and cmt:
        idx[(k, cmt)] = det          # 内容当键

# 写回时
hit = idx.get((entity, text))        # 命中才写
if not hit:
    unmatched += 1                   # 未命中保持空白，绝不猜
```

**为什么内容当键天然正确**：同一条记录横跨多天时，各天的正文字符串**本来就完全相同**——
用内容当键会自动覆盖整个区间，且**不可能贴到另一条记录上**。日期反而是个会漂移的弱键。

配套三条防御：

1. **输入缺正文字段 → 直接拒绝回填并退出**，不要退化成「那就按日期猜吧」
2. **未匹配的保持空白**，宁可覆盖率低也不填错
3. **回填前整目录备份**；发现错配当场 `rm -rf` + 整体回滚，不做局部修补
   （局部修补会留下你不知道的残余错配）

---

## ★验收判据：必须做内容一致性校验

**只看「回填成功 N 条」的日志发现不了这个 bug**，因为 N 偏大反而像好事。

正确的校验是逐条反查「被写入新字段的记录，其正文是否等于摘要来源的正文」：

```python
src = {(r['entity'], r['text'].strip()) for r in source_rows}
match = other = 0
for fp in glob(DAILY + '/*.json'):
    for r in json.load(open(fp))['items']:
        if not (r.get('detail') or '').strip():
            continue
        if (r['entity'], (r.get('text') or '').strip()) in src:
            match += 1
        else:
            other += 1      # ← 必须能逐条解释清楚 other 的来源
print(f"精确匹配 {match} | 其它来源 {other}")
```

`other` 不为 0 时**必须能说清每一条来自哪里**（本例 123 条来自当天另一条采集链路，
解释得通）。说不清的就是错配。

## 顺带：回填工具本身要「结构上无法编造」

写成两段式，脚本只做确定性部分：

```
tool.py --limit N          # 挑出待补条目，输出 JSON（脚本不生成任何文字）
  ↓  agent 联网检索、产出摘要
cat filled.json | tool.py --apply   # 按内容键写回
tool.py --stat             # 看覆盖率
```

- 脚本自身**一个字都不生成** → 结构上杜绝脚本编造
- `--apply` 匹配不到就跳过并报告，**绝不新增记录**
- 幂等：已有值的不覆盖，可中断续跑（挂 cron 每日增量也用同一个入口）

---

## 覆盖率口径要按「渲染范围」算，不是按文件总数

收尾时 stat 显示 98.4%（2499/2539），剩 40 条。逐条查后发现
**这 40 条全部属于已移出名册的实体，前端根本不渲染** →
对用户可见的范围而言是 100%。

报告时要说清楚这个口径差，否则「还差 40 条」会被当成未完成。
