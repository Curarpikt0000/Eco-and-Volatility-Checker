# 历史数据回填的完整性铁律（2026-08-23 实战，含一次真实的伪造事故）

适用：给「每人/每实体一条时间线」的数据集补历史（KOL 观点、机构评论、任何
`entity × date × content` 结构）。本页是**血泪教训**，不是理论。

---

## 事故复盘：按「日期就近」匹配 = 伪造历史

**做了什么**：给 2376 条快照历史条目补深度摘要。子 agent 只回了
`(kol, date, detail)`，我写的回填脚本按「(KOL, 日期就近) 回溯区间」把摘要贴回去 ——
理由是"同一条观点会横跨多天快照，取日期最近的那条即可"。

**症状**：1188 条输入，却回填了 **2160 条**。日志看起来像"超额完成"。

**真相**：**972 条被贴到了完全不同的另一条观点上**。
例：2025-12-18 的观点被贴上了 2026-04-08 的摘要。
因为"日期最近的下一条"根本不保证是同一条观点。

**这是伪造数据**，且只看回填日志完全发现不了。

### 为什么没有第一时间发现

`回填成功 2160 条` 这行日志本身没有任何异常信号。**发现它的唯一方式是做内容一致性
校验**：拿回填结果的 `comments` 和来源条目的 `comments` 逐条比对。

```python
# 事后校验（这段代码救了这次任务）
mis = 0
for 每个被回填的条目:
    if 目标条目.comments != 来源条目.comments:
        mis += 1
print("错贴", mis)   # → 972
```

### 修复：用内容当键，不用日期猜

```python
# ❌ 错：按日期就近回溯
cand = [x for x in src[kol] if x.date >= file_date]
target.detail = min(cand, key=lambda x: x.date).detail

# ✅ 对：按 (实体, 内容全文) 精确匹配
key = (kol, comments)            # 同一观点跨多天时 comments 字符串本就相同
target.detail = idx[key].detail  # 天然覆盖区间，且不可能贴错
```

**关键洞察**：同一条观点在多天快照里重复出现时，`comments` 全文是**相同的**。
用它当键，既天然覆盖了"跨天区间"，又在结构上杜绝了错配。日期只该用于**校验**，
永远不要用于**猜测归属**。

**额外保护**：输入缺 `comments` 字段就**拒绝回填**，不要退化成按日期猜。

## 窗口式回补：日期硬校验（防止子 agent 编日期）

第二类回填任务：让每人的历史「补齐到过去一年」，每人有各自的缺口窗口
`window_from ~ window_to`（因为每个人现有历史起点不同）。

风险点：子 agent 检索到一段没有明确日期的内容，为了交差**随便标一个窗口内的日期**。
这同样是伪造历史，而且比错配更难查——日期看起来完全合理。

### 四道关（`tools/apply_1yr_backfill.py` 已实现）

1. **日期硬校验**：每条 `date` 必须落在该人的 `window_from ~ window_to` 内，
   **越界一律拒收并列明细**。越界几乎必然意味着"无日期内容被硬标了个日期"。
2. **同日同文去重**：`(id, date, comments[:80])` 作键。
3. **只增量不覆盖**：既有条目一律保留。
4. **幂等**：可重复运行，再跑不产生重复。

### 父端必须独立复核，不能信子 agent 自报

子 agent 每一批都自报"日期越界 0"。**仍然要自己再验一遍**：

```python
oob = []
for r in rows:
    wf, wt = win[r['id']]                    # 从批次输入文件读窗口定义
    for rec in r['records']:
        d = rec.get('date','').strip()
        if not d or not (wf <= d <= wt):
            oob.append((r['id'], d, f"{wf}~{wt}"))
print("独立复核 — 越界", len(oob), "| 无来源",
      sum(1 for r in rows for x in r['records'] if not x.get('source')))
```

本次两轮 88 人 284 条，独立复核结果：越界 0 / 无日期 0 / 无来源 0 —— 通过。
（子 agent 甚至主动剔除了越界条目、以及与 `have_from` 同日的重复项。）

---

## 给子 agent 的 prompt 必须写死的三句话

1. **「日期必须落在 window_from ~ window_to 内。拿不准日期的宁可不要 ——
   把无日期内容随便标个日期就是伪造历史。父端会独立复核，越界一律拒收。」**
2. **「窗口内确实搜不到 → 返回 `records: []` 并在 note 写明原因。宁可 0 条也不凑数。」**
3. **「每做完 3 人就覆盖写一次盘」** —— 超时保命，见下。

## 增量落盘救回超时批次（实测有效）

一个子 agent 900s 超时，但因 prompt 强制"每 40 条落一次盘"，
**保住了 160/198**，只需补跑 38 条。
超时批次的正确处理顺序：**先查产物文件，再决定补跑范围**，不要整批重跑。

## 覆盖率判据要诚实，不要为了达标改数

回补后仍有大量人卡在距判据线 **1-10 天**的位置（如判据 2025-08-23，实际最早
2025-08-24 ~ 09-02）。这**不是回补遗漏**，而是那就是他们公开发声的起点/存档边界。

报告口径：
- 给严格达标数（≥365 天）**和**实质达标数（≥355 天）两个数
- 明确说明"再往前确实检索不到带日期的公开观点"
- **绝不为了凑达标率去编日期**

同理，「零条目」的人要逐一给出理由并让用户能判断合理性：
已故者（窗口内不可能有新观点）、同名干扰无法确认本人、缺口窗口仅 5-6 天期内无发声。
