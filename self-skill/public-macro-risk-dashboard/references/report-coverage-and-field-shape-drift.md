# 日报覆盖面漂移 + 上游字段形状漂移（2026-08-24 实证）

两类缺陷都**不报错、不告警、看板一切正常**，只有用户主动质疑才会暴露。放在一起是因为它们
共享同一个根因模式：**采集端在演进，消费端停在当初写死的样子**。

---

## 一、采集面 ≠ 报告面

### 症状
用户问：「这些基础数据是如何取得的？你基本上考虑了所有的表格，还是只考虑了其中一部分？」
答案是**只报了一部分**，而且差距极大。

实测（Eco-and-Volatility-Checker）：

| 项 | 数量 |
|---|---|
| dashboard section | **45** |
| cron 发报步骤点名的模块 | 6 部分骨架 + 5 个附加项 |
| `external_data` fetcher 总数 | **42** |
| cron 实际调用 | **38** |
| **抓了数据但从不进日报的板块** | **30+** |

压力四联图 / 国债拍卖 / 托管美债 / 信贷脉冲 / COMEX 全套 / 石油库存 / 市场广度 /
日经外资 / CIPS / AI 产业链 / IIP / 百年收益率 / 再融资墙 —— 全部每天照抓、照进看板、
从不上报。

### 根因
采集端随需求**逐次追加**（每加一个板块就改一次 fetcher + 渲染），
但报告端的措辞是**当初一次性写死的**，两者之间没有任何机制强制同步。
于是盲区**单向累积**，且永远不会自己暴露。

### 诊断三步（可套用到任何 cron 报告型管道）
1. 数**看板 section 总数** ← **报告实际点名的模块数**，差额就是盲区规模；
2. 列 **fetcher 全集** ← **cron 调用集合**，差集里区分「已弃用」与「真遗漏」；
3. 对每个「疑似没数据」的板块，**先读 fetcher 返回值再下结论**（见第二节）。

### ★判据顺序：先跑 fetcher → 再看渲染产物 → 最后才怀疑采集层

本次我先断言「欧洲央行是空的，因为那个 fetcher 没被调用」——**错了，自我推翻**。

真相：主 fetcher `fetch_cb_balance_sheets()` **本来就返回四家央行**，
欧洲那份 6 个资产项一直都在（黄金/外币资产/APP+PEPP 证券/对信贷机构贷款/银行券/存款便利），
看板早就渲染出总资产。**问题纯粹是报告文案从头到尾写着「三大央行」**，把第四家漏在了措辞里。
另有一个同名的独立 fetcher 属冗余，未被调用完全正常。

**跳过前两步直接归咎采集层，会把「文案缺陷」误诊成「数据缺失」，然后修错地方。**

### 结构性对策
- 报告骨架改为**固定模块清单**（本项目定为 12 模块）。
- 低频板块当期无更新，**也要占位输出一行「(季度/年度，本次无更新)」**，而不是整块消失。
  占位的价值不在信息量，而在**让人一眼确认「所有板块都被看过了」**——
  模块消失和模块无变化，在读者眼里长得一模一样，含义却天差地别。
- 增设「**数据健康度**」末节：列当期未就绪 / 抓取失败 / 校验不符项，
  **全部正常时也必须写一行「全部数据源正常」**，否则某个源悄悄挂掉不会有人知道。
- 用户明确要求：**不在乎日报长度，要的是关键信息全 + 分层结构清晰**。
  别为了短而砍模块。

### 改 cron prompt 的施工纪律
这类 prompt 里常内联着 `dashboard.generate(...)` 之类的长参数调用（本项目 **47 个参数**），
改别处极易误伤。**改完必须精确复核参数个数**：
找到 `generate(` 后**按括号配对取出完整调用体再数** `\w+=`。
不要用宽松正则——说明文字里往往也出现同名函数字样，会切错片段，
得出「参数丢了」或「一个都没有」的假警报（本项目历史上因此误判过两次）。

## 二、上游字段形状漂移：兜底必须放在消费端

### 症状
线上 build 直接崩：`AttributeError: 'list' object has no attribute 'strip'`。

某字段（`targets`）由 **LLM / 人工 / 历史脚本混合写入**，绝大多数是字符串，
但深度重抓时有 **7 条被子 agent 写成了数组** `["黄金$6000","白银$120","铜$7"]`。

### 比崩溃更危险的是不崩的那几处
同字段在取数层有 **4 处做 `[:150]` 截断** ——
**对数组切片完全不报错，会静默切成子列表**，数据悄悄变形，日志一切正常。

> 崩溃反而是好事（立刻暴露）；**静默变形才是长期数据污染的来源**。

**排查时不能只修报错那一处**，要把该字段的**所有取用点全列出来一起加固**
（本次共 7 处：渲染层 3 + 取数层 4）。

```python
# 找全部取用点
grep -n '\.get("targets")' src/*.py
```

### 处置原则：改消费端，不改上游数据
数组本身是**合法表达**（一条观点涉及多个标的），回头把它压成字符串反而丢结构。
正确做法是写一个归一函数，所有取用点统一走它：

```python
def _tgs(v, limit=None):
    """list → 顿号连接 / None → 空串 / 其它 → str()。"""
    if v is None:
        s = ""
    elif isinstance(v, (list, tuple)):
        s = "、".join(str(x).strip() for x in v if str(x).strip())
    else:
        s = str(v).strip()
    return s[:limit] if limit else s
```

### ★踩坑：加辅助函数前先查重名
给归一函数取的短名（`_tg`）**与文件里一个已有的局部变量同名**，
函数在运行时被那个变量覆盖，后续调用报 `'str' object is not callable`——
**一个本来只是「加固」的改动，反而制造了新的崩溃点。**

更讽刺的是：那个同名局部变量所在的代码段**本来就已经正确处理了数组**，
说明这个坑之前有人踩过、局部修过，但**没有上升为全局约定**。

教训：
1. 短命名（`_x` / `_tg` 这类）在长文件里极易撞名，加函数前先
   `grep -n '\b<名字>\b' <file>`；
2. **发现某处已有针对性防御，说明这是系统性问题**，应就地推广为公共函数，
   而不是各修各的。

## 三、维度在写入环节被静默丢弃（同一模式的第三种表现）

COMEX 交割榜要区分 **C(Customer 代客通道)** 与 **H(House 自营盘)** ——
这是两个**独立账户**，代表完全不同的含义（通道 vs 机构真实观点），不能合并统计。

链路上 CME PDF 的 `FIRM ORG` 列有 C/H，解析器 `s['org']` **也一直抓着**，
但生成中转文本的那两行**只写了机构名+手数，把 org 丢了**：

```python
# 坏：Jp发13          ← org 在这里被扔掉
# 好：Jp(H)发13       ← 带出账户类型
```

下游正则同步放宽即可向后兼容：

```python
r"([A-Za-z][A-Za-z0-9]*)(?:\(([CHch])\))?(发|接)(\d+)"
# 有标记 → 计入 i_c / i_h；无标记 → 计入 i_u(未知)，绝不臆测归类
```

**通用教训：一个维度在「解析 → 中转格式 → 消费」三段链路里，
只要任何一段的序列化没带上它，它就会静默消失，且下游完全无从察觉。**
排查「某维度为什么没有」时，**逐段打印中转格式的原始文本**，
不要只看两端（解析器有 / 消费端没有 → 中间那段才是凶手）。

### 附带的现实约束
改完两端后要核实**改动是否真的会生效**：
- 已写入的历史记录仍是旧格式 → 覆盖率不会追溯改善；
- 本次还发现上游采集 cron **已被用户主动删除**，
  意味着改好的解析器**当前没有任何调度会调用它**。
- **必须如实报告这两点**，不能让「代码已改」被误读成「问题已解决」。
