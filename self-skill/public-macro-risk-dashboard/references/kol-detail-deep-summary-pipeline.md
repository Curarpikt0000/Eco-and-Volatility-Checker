# KOL 观点「深度摘要」：加一个字段要走完整条链路

Companion to `kol-roster-and-drilldown-sections.md`（那篇讲名册与两层钻取 UI）。
这篇讲 2026-08-23 Chao 的这条反馈引出的一整类问题：

> 「我点开第二个层级发现和最初的默认值没有任何区别。他们可能是一个 1 小时的 YouTube
>  或 59 页报告，我需要你给我总结至少 100 字最多 300 字带格式的方便阅读。」

---

## 0. 先判定：是渲染 bug，还是数据本来就只有一句话？

不要直接去看前端。**先量化数据层**：

```python
ls = sorted(len(str(x.get('comments') or '')) for x in json.load(open('data/kol_independent.json'))['all'])
# 实测: 中位 32 字 / 最长 51 / >=100 字的 0 条
# 字段清单: ['kol','sector','direction','targets','comments','date']  ← 根本没有 detail 字段
```

结论一眼可见：**展开层复用同一个 `comments`，所以两层永远一样 —— 不是渲染 bug，是数据缺失**。
前端 `rowHtml` 里那行 `'<div class="kd-full">' + esc(cmt) + '</div>'` 只是症状。

★ 这个判定顺序能省掉一整轮白改前端。同类症状（"点开没内容 / 点开和外面一样"）
先跑上面三行，再决定动哪一层。

## 1. ★★ 新字段必须走完整条链路，漏一跳就静默退化

这是本次最贵的教训。`detail` 从产生到显示要经过 **5 跳**，我一开始只改了两跳，
结果 build 出来仍然是一句话：

| # | 环节 | 文件 | 漏了会怎样 |
|---|---|---|---|
| 1 | 抓取产出 | 子 agent → `scratch/<batch>/out/<id>.json` | 无数据 |
| 2 | 聚合入库 | `data/kol_independent.json` | 当日卡片无 detail |
| 3 | **每日快照** | `save_kol_daily_snapshot()` | 快照渲染路径退回一句话 |
| 4 | **历史合并** | `kol_full_history()` 的 **两路都要传**（snapshot + backfill） | 历史条目拿不到 detail |
| 5 | **内嵌 payload** | `_kol_history_payload()` 数组扩位 | 前端读不到 |
| 6 | 前端渲染 | `rowHtml()` | 有数据也不显示 |

第 3、4 跳是我实际漏掉的。症状是"数据文件里明明有，页面上就是没有"。

**通用做法**：给这类多跳管线加字段时，先把链路列出来，逐跳 grep 字段名，
每跳都断言一次。验收要在**最终产物**上数：

```python
m = re.search(r'\n  var DATA = (\{.*?\});\n', h, re.S)      # 变量名要先确认!
p = json.loads(m.group(1).replace('<\\/','</'))              # payload 做过 </ 转义
wd = sum(1 for v in p.values() for r in v['h'] if len(r)>=7 and r[6])
```

⚠️ 我先用 `var KOL_HIST` 去匹配，返回"未找到 payload"，差点误判成没进产物 ——
**内嵌 JSON 的变量名要先从源码确认**（这里是 `var DATA = {kol_history_json}`）。

## 2. detail 的格式契约（Chao 认可的形态）

100–300 中文字，四段，每段 `▸ ` 开头、`\n` 分隔：

```
▸ 核心论点：他的主要判断是什么
▸ 关键依据：引用了什么数据/逻辑，尽量带具体数字
▸ 时间与位置：时间窗口、点位、目标价；没有就写「未给出具体点位」
▸ 标的与操作：涉及哪些资产，买/卖/观望
```

前端按 `▸ 小标题：内容` 正则拆成 `.kd-seg`（左侧固定宽度的键 + 右侧值），
折叠行加一个「详」徽章标识该条有深度摘要。`comments` 保持 ≤40 字做折叠态。

实测效果（Jordan Roy-Byrne）：折叠「跌破 200 日均线是二次上车机会」→
展开出「对比 1972 年突破后 29% 下跌 / 本十年结束前 8000–9000 美元 / 7–10 年 2 万–5 万」。

## 3. ★ 反编造纪律：宁可标 thin/none，不许凑字数

字数是硬指标，很容易诱发编造。必须在 prompt 里写死三档：

| status | 触发条件 | detail 内容 |
|---|---|---|
| `ok` | 检索到实质内容 | 正常四段 |
| `thin` | 公开信息只有一两句 | 「公开信息有限，仅检索到：<原文要点>」 |
| `none` | 完全搜不到 | `""`，且 `direction="未找到"` |

健康分布参考（124 人全量）：**110 ok / 13 thin / 1 none**。
若某批 100% 全 ok，反而要怀疑在凑字数。

真实 thin 样例（可用来校准）：某微软高管公开信息只有产业层面表态（裁员、主机涨价），
无任何宏观市场观点 → 如实写明「未发表宏观市场观点」，**不硬编 300 字**。

同理，历史回填时「原文没给目标价」一律写「未给出具体点位」，**禁止推算补全**。

## 4. 并发抓取的落盘纪律

124 人 / 6 路并行 / 每路 ~20 人 25 分钟预算。两条硬要求写进子 agent prompt：

- **每人搜完立即单独落盘** `out/<id>.json`，不要攒到最后统一写
  （曾因超时把整批成果全部丢失）。
- 每人 web_search ≤3 次、web_extract ≤2 次，抓不到就跳过，不要死磕单个人。

聚合时严格按名册对齐，并报告双向差异：

```python
missing = [i for i in by_id if i not in recs]   # 名册有但无结果 → 保留旧值, 不清空
extra   = [i for i in recs if i not in by_id]   # 结果有但不在名册 → 丢弃
```
本次 124/124 零缺失。**无结果时保留旧值**，绝不覆盖成空（幂等写入的老坑）。

## 5. 历史回填：先量规模，往往比想象小

被要求「所有人过去一年的都 backfill」时，先统计再报工期：

```python
# 实测: 114 个文件 / 369 条历史 / 0 条有 detail / 325 条在近一年内 / 人均仅 3.2 条
```

★ 关键发现：**这批历史的 `comments` 本身已有 150–200 字**（不像当日抓取只有 32 字），
所以多数条目只需**重组为四段**，不必联网。子 agent prompt 里明确写：

> 先看 comments 能不能直接拆成四段 —— 大多数可以，不需要联网。
> 只有 comments <60 字且 source 可用时，才用 web_extract 抓一次。
> **不要为每条都联网**，全联网会超时。

结果：369/369 完成，359 ok / 10 thin，联网次数仅 ~40 次（约 10%）。

## 6. 回填工具的防编造设计（可复用）

`tools/backfill_kol_detail.py` 的设计要点 —— **脚本自身不生成任何文字**：

- `--limit N` 列出待补清单（按日期降序，最近优先）→ agent 据此检索
- `--apply` 从 stdin 读回 agent 产出的 JSON 写盘
- `--stat` 看进度
- 幂等：已有 detail 的条目跳过，可中断续跑
- `--apply` 用 `(file, date)` 二元组定位，**匹配不到就跳过并报告，绝不新增条目**

把"挑选+落盘"（确定性）和"产生文字"（需检索）拆开，**结构上杜绝脚本编造**。
这个形状适用于任何"给存量数据补 LLM 生成字段"的任务。

## 7. 挂进 cron，否则次日全部白做

★ 最容易忘的一步。每日 cron 会重跑 KOL 抓取并**覆盖** `kol_independent.json` ——
不同步升级 cron prompt，今天的深度数据明天就没了。

改两处：
- 步骤 3：从"一句话"改为深度摘要模式，把 §2 格式契约 + §3 反编造纪律**原文写进 prompt**，
  并加一句「**绝不能只写 comments 不写 detail**」。
- 新增步骤 3b：`python3 tools/backfill_kol_detail.py --limit 25` 每日增量补历史，
  失败标 SKIP 不中断主流程。
