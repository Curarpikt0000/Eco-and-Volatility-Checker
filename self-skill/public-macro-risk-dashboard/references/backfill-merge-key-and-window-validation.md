# 历史回填的合并键与窗口校验（防止静默伪造历史）

回填（backfill）类任务最危险的失败模式**不是报错，而是「回填成功 N 条」的日志看起来超额完成，
实际上把 A 的内容贴到了 B 身上**。本页记录一次真实的自造 bug 与最终的正确做法。

---

## 一、★用「日期就近」当合并键 = 伪造历史

### 我犯的错
给 KOL 历史观点回填摘要时，第一版脚本按
「**(人物, 日期就近) 回溯区间**」把子 agent 产出的摘要贴回去。

日志显示：**1188 条输入 → 回填了 2160 条**。看起来像「一条观点跨多天被正确展开」。

### 实际发生了什么
「日期最近的下一条」**可能是完全不同的另一条观点**。
实测 **972 条错配** —— 例如 2025-12-18 的观点被贴上了 2026-04-08 的摘要。

**这就是伪造。** 而且从日志上完全看不出来，只会觉得「超额完成」。

### 发现它的唯一方法
做**内容一致性校验**：回填后逐条比对
「被写入条目的 `comments`」 vs 「摘要来源条目的 `comments`」是否为同一条。
不做这一步，这个 bug 会一直躺在数据里。

### 正确做法：用内容当键，不用日期猜
```python
# 坏：按 (kol, 日期就近) 回溯 → 会贴到别人的观点上
# 好：按 (kol, comments 全文) 精确匹配
key = (kol, (comments or "").strip())
```
同一条观点跨多天出现时 `comments` 字符串**本就相同**，
用内容当键**天然覆盖区间**，且不可能贴错。

配套保护：
- **输入缺 `comments` 字段就拒绝回填**，绝不退化成按日期猜；
- 未匹配上的**保持空白**，不猜、不就近凑。

修正后：**1188 输入 → 精确回填 1188 条，零错贴**（不再是虚高的 2160）。

## 二、跨窗口回填必须做「日期硬校验」

给每人补「过去一年缺失窗口」的历史时，子 agent 可能把**无日期的内容随便标一个日期**
塞进窗口里——这同样是伪造历史。

### 四道关（写进回填脚本，不靠子 agent 自觉）
1. **日期硬校验**：每条记录的 `date` 必须落在该人的 `window_from ~ window_to` 内，
   **越界一律拒收并报告**。越界即意味着日期是编的。
2. **同日同文去重**：`(id, date, comments[:80])` 相同只保留一条。
3. **只增量不覆盖**：既有条目一律保留。
4. **幂等**：可重复运行，再跑一次不产生重复。

### ★父端必须独立复核，不信子 agent 自报
子 agent 每批都会报「日期越界 0」。**不要采信**，父端用自己的窗口定义重算一遍：

```python
# 独立复核：越界 / 无日期 / 无来源
for r in rows:
    wf, wt = win[r['id']]          # 父端自己持有的窗口定义
    for rec in r.get('records') or []:
        d = (rec.get('date') or '').strip()
        if not d:                    nodate += 1; continue
        if not (wf <= d <= wt):      oob.append((r['id'], d, f"{wf}~{wt}"))
        if not rec.get('source'):    nosrc += 1
```
本次两轮 88 人 / 284 条，父端复核结果：**越界 0 / 无日期 0 / 无来源 0**，
且子 agent 主动剔除了越界条目与和 `have_from` 同日的重复项——说明把判据写死在 prompt
里确实有效，但**验证权必须留在父端**。

## 三、prompt 里要写死的反凑数纪律

子 agent 天然倾向「凑够数量」。必须显式授权它交白卷：

- 「**拿不准日期的条目宁可不要**，绝不允许把无日期内容随便标个日期——那是伪造历史。」
- 「窗口内确实搜不到 → 返回 `records: []` 并在 `note` 里写明原因。**宁可 0 条也不凑数。**」
- 「**每做完 3 人就覆盖写一次盘**」——超时时保住已完成部分
  （本次 sn7 批次 900s 超时，因为有这条纪律保住了 160/198，只需补跑 38 条）。

零条目是**合理结果**，理由要能自洽：已故者（窗口内不可能有新观点）、
同名干扰无法确认本人、缺口窗口仅 5-6 天期内无公开发声。

## 四、覆盖率判据要说清口径，别用一个数字糊弄

同一批数据，不同口径差很多：

| 口径 | 结果 |
|---|---|
| ≥365 天（严格） | 35/122 |
| ≥355 天（实质达标，差 ≤10 天） | **52/122 = 42.6%** |
| 只看 backfill 文件 | 34 满一年 |
| 算上每日快照 | 无历史者仅 1 人 |

**报告时必须讲明白哪个口径**，并说清「不达标」的真实原因：
本次大量人卡在 2025-08-24~09-02，**距判据线只差 1-10 天**，
那是他们公开发声的起点/存档边界，**再往前确实检索不到带日期的公开观点**，
不是回补遗漏。

比「覆盖率 42.6%」更有信息量的指标是**改善幅度**：
**80 人历史起点被推前，平均前推 120 天，最多 361 天。**
