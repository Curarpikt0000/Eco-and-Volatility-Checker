# 字段形状漂移与跨项目丢字段：兜底放消费端，根因修生产端

> 2026-08-24 两个真实故障，同一主题的两面。

## A. 上游字段形状漂移 → 线上 build 实崩

**症状**：每日 build 报 `AttributeError: 'list' object has no attribute 'strip'`，
整个产物生成失败。若不修，次日 cron 直接发不出日报。

**根因**：某字段由 **LLM / 人工 / 历史脚本混合写入**，类型迟早漂移。
本次绝大多数是字符串，**7 条被子 agent 写成了数组**。

### ★比崩溃更危险的是不崩的那几处

同字段在取数层有 4 处做 `[:150]` 截断 ——
**对数组切片完全不报错，会静默切成子列表**，数据悄悄变形，日志一切正常。

> 崩溃反而是好事（立刻暴露），**静默变形才是长期数据污染的来源**。

**排查纪律：不能只修报错那一处**，要把该字段**所有取用点**列出来一起加固。
本次共 7 处（渲染层 3 + 取数层 4）：
```python
[(m.start(), src[m.start()-70:m.start()+70]) for m in re.finditer(r'\.get\("字段名"\)', src)]
```

### 处置原则：改消费端，不改上游数据

数组本身是**合法表达**（多个标的），回头压成字符串反而丢结构。
正确做法是写归一函数，所有取用点统一走它：

```python
def _tgs(v, limit=None):
    if v is None:            s = ""
    elif isinstance(v, (list, tuple)):
        s = "、".join(str(x).strip() for x in v if str(x).strip())
    else:                    s = str(v).strip()
    return s[:limit] if limit else s
```

### ★★踩坑：加辅助函数前先查重名

我给归一函数取的短名与文件里一个**已有的局部变量同名**，
函数在运行时被那个变量覆盖 → `'str' object is not callable`。
**一个本来只是「加固」的改动，反而制造了新的崩溃点。**

更讽刺的是：那个同名局部变量所在的代码段**本来就已经正确处理了数组** ——
说明这个坑之前有人踩过并局部修过，但**没有上升为全局约定**。

**两条教训**：
1. 短命名（`_tg` / `_x` 这类）在长文件里极易撞名，加函数前先
   `grep -n '\b<名字>\b' file.py`。
2. **发现某处已有针对性防御 = 这是系统性问题**，应就地推广为公共函数，
   而不是各修各的。

## B. 跨项目丢字段：解析拿到了，写出时丢了

**症状**：下游某维度覆盖率从 100% 断崖到 0%，且恰好与「上游换数据通道」同期。

**根因定位路径**（本次 COMEX 账户类型 C/H）：
1. 先确认**解析器有没有抓到** → `grep -n "org" parser.py` 发现 L110/L127
   一直正确抓取并存进结构体 → **不是采集问题**。
2. 再看**生成下游文本的那一步** → `to_activity_note()` 只用了 name+数量，
   **把已经在手的字段丢了**。
3. 结论：字段在源头存在、在中途丢失、在下游表现为「数据缺失」。

**修法只有 3 行**（在已有结构体上取字段拼进文本）：
```python
def _tag(s):
    o = (s.get("org") or "").strip().upper()
    return f"{short(s['name'])}({o})" if o in ("C","H") else short(s["name"])
```

**下游同步兼容新旧两种格式，缺失一律标未知、绝不臆测归类**：
```python
r"([A-Za-z][A-Za-z0-9]*)(?:\(([CHch])\))?(发|接)(\d+)"
# 带 (C)/(H) → 精确计入 _c/_h ；不带 → 计入 _u(未知)
```

### 改动落在别人的生产 repo 上时

用户明确要求：**「你在 README 或者某个地方写一下你的改动，然后可以先 push，
我让另外一个 agent 去 evaluate 一下。」**

→ 写 `CHANGE_NOTE_<日期>_<主题>.md` 与代码同一次提交，必须包含：
- 一句话说明 + 为什么改（带用户原话）
- **具体 diff 片段**与新旧输出对比（用真实数据跑出来的）
- **兼容性检查清单**：明确点出「若你另有下游按旧正则解析，新格式会漏读，请 grep 确认」
- 验证记录（哪个真实样本、结果与原始字段是否一致）
- 「如评估后有冲突请直接 revert 并说明原因」

### 历史回归前先算清能不能补回来

用户要求「把所有能找到的 PDF 全都重新采集一遍」时，**先核对现状再动手**：
本次强制全量重跑，结果与重跑前**总量、天数一分不差** ——
因为存档早已 100% 解析入库，缺的那两个月**根本没有源文件**。

> 回归跑不出新数据 ≠ 回归失败。**要如实说「跑了，没有新东西，原因是 X」**，
> 而不是让用户以为补上了。

## 通用判据

| 现象 | 先查什么 |
|---|---|
| 下游某维度突然全空 | 解析器是否仍抓到 → 中途写出时是否丢了 |
| 某板块不在报告里 | fetcher 返回值 → 渲染产物 → 最后才怀疑采集 |
| 覆盖率断崖 | 是否与「换数据源/换通道」同期 |
| 想靠回归补历史 | 源文件在不在那个时间段，不在就补不回来 |
