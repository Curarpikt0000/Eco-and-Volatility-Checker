# 板块「是否真在更新」核查 + 上游停更 + House/Customer 口径 + 菜单顺序(2026-10-06 实战)

## 1. cron 标 ok ≠ 数据是活的
- 日报 cron 的 build_dashboard.py 一次生成 64 个板块,板块「进了 cron」不等于「数据在动」。
- 典型事故:库存 + GLD/SLV 图读外站 comex-inventory-charts.pages.dev,该站自己停在 09-16 共 20 天,页面照常渲染、cron 照常 ok,无人发现。
- 核查三步(别用「页面里最新日期」粗扫,会误判):
  1. 找板块 fetcher 读的是哪里(外站 / data/*.json 缓存 / 自抓 API / manual_overrides)。
  2. 现场读源头最新数据日(独立请求,不经我们的缓存)。
  3. 找生产者是谁、跑在哪台机器、cron 是否存在。本例生产脚本写死 Mac 路径,VM 上无对应 cron。
- 「读别人产出」的板块风险最高。fetcher 应:先自产 → 失败回落外站 → 再回落缓存,并把 source/tried 写进 note,不得静默回落。
- WGC 周数据天然滞后约 10 天(asOfDate 停在上周五)属正常,别误报。

## 2. Notion 里分不清「谁写的」
- 本机 token 与 Mac 上 agent 常是同一个机器人账号,读 last_edited_by 无法区分机器。
- 不要因「Notion 今天有新行」断言「Mac 采集 cron 还在跑」——这是推断不是证据。
- 避免撞车:对共享 Notion 库纯只读,只在「生成图 + 推站」一环接管。

## 3. 采集模式缺口的识别
- Notion 日行 Parse Status='OK (stock)' = 只写库存,没有 [Delivery] 段、OI 空。周四几乎每周如此(08-20 起)。
- 剔除美国休市日(Juneteenth / 7-4 休市日 / Labor Day)后按星期统计真缺失,才看得出规律。
- 缺失周图上必须标注:悬停写「本周仅 N/5 个交割日」,不足 5 天且该周已过完 → 浅色虚线柱;标题覆盖天数用各周 days 之和,别用「历史 PDF 数」(会漏增量日)。

## 4. House(H) vs Customer(C) 口径(Chao 2026-10-06:做市商图只要 House)
- Notion Activity Note 自 08-21 起带 `名称(C)/(H)发N`;旧解析正则捕获了 org 却丢掉 → C 与 H 被加总。
- 影响巨大:黄金 09-28 周含 C 为 −1970,只算 H 是 +805,符号反了,「做市商囤货/看涨」结论不成立。
- 数据三段:PDF 段(01-06~06-05)每周有 org 列;Notion 06-06~08-20 无标记(不能证明是 H,不得假装);08-21 起有标记。
- 落地:聚合按 org 分 H/C/U 三层,只累计 H;整周全是 U 的周 blank=True,数值置 None,图上留白(浅灰细线占位),不画 0。
- PDF 段 JPM 几乎全是 C(H 仅 106 手),改口径后历史曲线形状会大变,要提前告知用户。
- PDF 与 Notion 两段无重叠日期,无法逐笔证明两段 H 同口径,只能证明 org 语义一致,要如实说。

## 5. 验证纪律
- 改聚合口径后用另写的独立算法对账(先按 H 单独聚合 12 个周值,再与新代码逐一比对 12/12),不要只信自己新写的代码。
- 隔离整站构建会写生产 Notion(国债压力、OFR 金融压力指数),构建前先关 Notion 写入步骤;副本构建的价格可能比线上旧一天,别据此发布。
- 无头 Chromium 可用(--headless=new --no-sandbox --screenshot= 或 --dump-dom);vision_analyze 的数字是估读,必须用数据核。
- 「接入」类改动先在函数层实测(fetch 返回的 as_of/source),再如实说「整站没验证」,不夸大。
- 回复前先对上用户的选项编号:Chao 回「1 同意 2 A 3 ok」对应的是我上一条的三问,我曾没认出来又问一遍。
- 公司 pre-commit 钩子需 ussh 证书,过期时提交失败:不绕钩子,说明暂存区没丢、本地=远端,请 Chao 刷新后再提交。

## 6. 分组菜单与页面顺序错位(「跳动感」根因 + 根治)
- 根因:scrollspy 用 DOM 序号判当前节,菜单却按关键词分组渲染,同组成员即便相距几十屏也被并成一组 → 菜单自上而下读,页面 y 倒退。实测 64 板块有 3 处倒退;另有 15 个板块没命中任何关键词掉进「其他」。
- 根治:菜单严格按 DOM 顺序分段渲染。无命中的并入相邻段;夹在同组两侧的孤立项归入两侧;同组被隔开则第二段标「(续)」。
- 代价:组标题变多(本例 9→15),需先告诉用户。
- 验收:本地起无头 Chromium,把探针 script 注入页面末尾,2.5s 后写 {dom:[{id,t,y}], menu:[{g,href,t}]} 到 <pre id=PROBE>,用 --dump-dom --virtual-time-budget=12000 取出。判据:菜单 href 缺失 0;按菜单顺序读页面 y 倒退次数 0;菜单 id 序列 == DOM id 序列。
- 不必整站重建:把新菜单脚本段套进现有 docs/index.html 同位置即可验证。
- 坑:第一版探针报「菜单项数 0、一致 True」是空集合的假一致,须先断言集合非空;验证脚本不要夹带已执行过的改源码步骤,否则再跑会 substring not found 且用的是旧产物。
