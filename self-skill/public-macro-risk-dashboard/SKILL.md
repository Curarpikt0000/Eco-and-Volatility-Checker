### The independent daily-snapshot data-vault pattern (v3 mechanics — reusable for ANY derived metric you want to own)

When you currently READ another agent's Notion DB but the owner wants a genuinely independent, self-owned second source with cross-period comparison, you MUST accumulate your OWN history (a single overwritten daily file can't diff across days). The proven build:

- **`save_kol_daily_snapshot(date_str=None)`** — after the daily crawl, persist the FULL current directions (`kol_independent.json`'s `all`, 91 rows) to `data/kol/daily/YYYY-MM-DD.json` (`{date,count,source,kols:[{kol,sector,direction,targets,comments}]}`). Idempotent (same-day re-run overwrites; verified two runs → identical md5). This git-tracked dir IS the independent data vault (public repo → snapshots go in git; `.env` never). `data/kol/` is NOT in `.gitignore` — the daily cron's full `git add` picks it up automatically.
- **`load_kol_daily_snapshots()`** → `{YYYY-MM-DD: {kol: {...}}}` across all snapshot files.
- **`kol_weekly_changes()`** — diff **本周最新快照 vs 上周最后一天快照** (this-Monday / last-Monday boundaries computed from `date.today()`), emit a turn per KOL whose `direction` changed. A KOL with NO last-week record is SKIPPED (newly-covered ≠ "turned"). If cross-week snapshots don't exist yet, honestly fall back to earliest-vs-latest; **if only ONE day of snapshots exists, return `[]` — never fabricate a turn.** Verified: with a synthesized last-week snapshot it correctly picks the上周 file as baseline (not yesterday), proving the week-boundary logic.
- **`kol_stance_changes_grouped()` now sources `kol_weekly_changes()` ONLY** — `fetch_kol_recent`/`kol_stance_changes` (the other-agent-DB path) are DEPRECATED, no longer the主源. Returns `{since, days, total, modules:[…]}` unchanged in shape so the renderer didn't move.
- **Honest empty state is EXPECTED at first.** Because past days' FULL directions were never retained (only today's snapshot existed pre-v3), the block is legitimately EMPTY ("本周暂无 KOL 主导方向变化（或快照尚在累积中）") until ≥2 cross-week snapshots accumulate (~next Monday). This is the 绝不编数字 rule, not a bug — tell the user "attaches automatically once snapshots accrue," and OFFER (don't auto-do) a one-time seed backfill from the other agent's by_day DB if they want content NOW.
- **Render + sector-归一 unchanged from v2** (kept because Chao said Q1-satisfied): `_KOL_SECTOR_MAP` (maps BOTH the 中文 independent-vocab AND any 英文 vocab → one 中文 module + 英文 subtitle + `_KOL_SECTOR_COLOR`; unmapped→"其他"); `_kol_changes_html` = top overview + one `.h-module` per sector (title bar `background:color` + 转向数 badge) + `.kol-mod-inner` KOL cards, each with a **shift badge** (rank `强烈看空 -2 … 强烈看多 +2`; new>old ⇒ `▲转多` clay红; new<old ⇒ `▼转空` sage绿 = 逆向 buy-point, matches "falling=green"; equal ⇒ `→微调`) + prev→new chips + 言论 + 标的. Backward-compat: a plain `list` gets wrapped in one "全部" module.
- **Threading:** `build_dashboard.py` calls `save_kol_daily_snapshot()` BEFORE `kol_stance_changes_grouped()` (so today's snapshot exists for the diff); template part-title 当日/上周至今 → **"本周 KOL 状态变化 · 按模块"**; the daily cron already full-`git add`s `data/kol/` so no push change needed.
- **Window is a one-place preference:** the weekly boundary lives in `kol_weekly_changes()`; a "改成上两周/当周" ask changes that comparison there. Same "widen window + group-by-category when a block looks empty at单日 frequency" move as the 13F holdings module-grouping (both use `.h-module`).

### ★VIEWS (观点全景) vs CHANGES (转向) — a Chao correction: a turn-only block is TOO NARROW (2026-08)

Right after the v3 changes-block shipped EMPTY (correctly — only 1 snapshot, no cross-week diff yet), Chao pushed back: *"本周你没找到任何有意义的更新吗？…不可能 88 个 KOL 这一周什么话都没说吧？…按不同模块把这周有意义的、新的 KOL 观点，按卡片和多空方向呈现"*. The lesson: **"状态变化 (direction TURNED)" and "本周有意义的观点 (what everyone SAID)" are two different products — a diff-only block shows near-nothing most weeks and reads as broken, even though 60+ KOLs have substantive opinions.** The fix is a SECOND, complementary block, NOT replacing the changes block:
- **`kol_weekly_views(min_comment_len=10)`** — every KOL with a substantive comment (not just those who turned), grouped by sector. Source = the SAME independent snapshots (latest day's snapshot preferred; fall back to `kol_independent.json`'s `all`). Returns `{date,total,modules:[{sector,en,color,views:[{kol,direction,comments,targets,date}]}]}`. Filter out empty/near-empty comments (`len < min_comment_len`) so "有实质观点" is real, never padded. This session: 60 of 91 KOLs had real views across 7 sectors — proving the "nobody said anything" impression was a block-design artifact, not reality.
- **`_kol_views_html`** — one card per KOL with a **多空方向 badge** (`.kv-badge`: 强烈看多 clay红填充 / 看多 浅红 / 分歧·中性 灰描边 / 看空 浅绿 / 强烈看空 sage绿填充 — warm=bull, cool=bear, matches the falling=green semantics) + 言论 + 标的, grouped into the same `.h-module` coloured sector boxes as 13F/changes. Sort views within a module by direction strength (看多 first, most-eye-catching), modules by view-count desc.
- **Layout:** the VIEWS block ("本周 KOL 观点全景 · 按模块 (多空方向卡片)") goes ABOVE the CHANGES block ("本周 KOL 状态变化 · 按模块 (态度转向 call-out)") — 观点全景 is the primary always-populated content; 转向 is the secondary call-out that fills once snapshots accrue. Standard `generate()` kwarg `kol_views=None` + `{kol_views}` template slot + `.format` + `build_dashboard.py` threading.
- **SECTOR-MAP dedup gotcha:** `_KOL_SECTOR_MAP` had "贵金属" and "贵金属与商品周期" mapping to TWO distinct 中文 modules → the same domain split into two boxes. Chao's data uses both vocab strings; collapse synonyms to ONE canonical 中文 module (both → "贵金属") so a sector isn't fragmented. When adding any grouped block, audit the sector map for synonym pairs that should merge.
- **General rule:** when a "what changed" block is legitimately sparse, the user usually ALSO wants a "what's the current state / what did everyone say" companion block — offer both (a diff view AND a full-snapshot view), don't make the diff view carry both jobs.

### ★Per-opinion DATE labeling — you CANNOT date a comment from a snapshot that only records CRAWL-day (Chao correction 2026-08), and the fix he directed (import sibling agent's by_day HISTORY as a time-series seed)

Chao noticed every views-card carried the SAME date (the crawl day) and asked to label when each person actually said it. The hard truth: **the independent daily snapshot only stores the CRAWL date, not the言论's original发表日** — so a uniform crawl-date on every card is MISLEADING (implies everyone spoke that day). Two-part handling:
1. **DON'T regex-extract a 发表日 from the comment text — it produces WRONG dates.** Comments contain date-shaped noise that is NOT a publication date: price-target years (7-8k 2028-30), forecast years (奇点2029/2045), price ranges (崩至25-30). A naive digit-dash grab mislabels these as the speak-date, violating 绝不编. Chao chose **Option A: just REMOVE the misleading uniform date** from the card header (keep KOL+方向+言论+标的). Real dates the KOL themselves wrote INTO the comment (8/3发, 8/12发, 8/10 BNN) stay naturally inside the言论 text — trustworthy because self-stated, and survive un-touched when you drop the header date. Unlabelled-when-unknown beats guessing.
2. **The DURABLE fix Chao then directed — seed a real time-series so future crawls CAN date opinions: import the sibling agent's by_day HISTORY into your own vault.** The insight (记住这个 general lesson): **without cross-day HISTORY you cannot distinguish a NEW opinion from a REPEATED one — a single-day snapshot has no first-seen baseline, so you can't tell if he just said it today or has held that view for two months and merely repeated it.** Import mechanics (probed this session): the other agent's Notion by_day DB (KOL_BY_DAY_DB, read via fetch_kol_recent(days,limit)) covers roughly 2026-01-06 to present, ~191 days, 94 KOLs, ~2339 rows — exactly the time-series底座 needed. One-time seed = pull that history, write it into data/kol/daily/YYYY-MM-DD.json per day (same schema as save_kol_daily_snapshot), git-push (public repo). AFTER seeding, each new daily crawl can diff against accrued history to compute a per-opinion **first-seen date** — THAT is the honest date label, replacing the removed crawl-date. This is a legitimate ONE-TIME historical bootstrap of an independent vault (not an ongoing dependency — going forward Eco crawls itself), so it does NOT contradict the v3 own-your-metric decoupling.
    - ★**EXECUTED 2026-08 — the import is DONE + the first-appearance logic is BUILT, with an honest粒度 caveat.** `scratch/import_kol_history.py` (one-shot) pulled `fetch_kol_recent(days=240, limit=20000)` → grouped by date → wrote **205 day-snapshots (2025-12-18→08-13)** into `data/kol/daily/` (skips days that already exist, e.g. Eco's own 08-14), each `{date,count,source:"imported from by_day DB",kols:[…]}` (sector = `detail_sector` 中文优先 else `sector`). Total vault now 206 snapshots, 1.6M (well under any size红线; snapshots go in git — public repo). Committed 1589cb2, pushed.
      - **`kol_weekly_views` now emits `since_date` (当前方向连续保持的起始日, 回溯快照) + `is_new` (起始日 ≥ 本周一 ⇒ 本周新观点).** `_kol_views_html` renders `🆕 本周新观点` (clay红) or `自 <date> 持此观点` (muted). This is the honest replacement for the removed crawl-date — a per-opinion first-seen date computed from accrued history, not regex-guessed from comment text.
      - ★★**THE粒度 REALITY to state honestly: the imported by_day history is SPARSE (that agent covers only ~6–13 KOLs/day), while Eco's own daily crawl is DENSE (all 91 in one shot).** So when回溯 from Eco's 08-14 dense snapshot into the sparse history, almost every KOL "断档" on the prior (sparse) day → `since_date` stops at 08-14 → **currently ALL 60 views label "本周新观点".** This is NOT a bug — it's the two-source粒度 mismatch. ## Reusable techniques proven this build (the durable lessons)

- ★Most anti-scrape sources actually work with a PLAIN browser UA — don't over-defend with Jina (2026-08 correction, supersedes the old web_extract-first advice). Chao pushed back on 未找到 answers (不能接受没有尝试就放弃… 这些明明有很多网站都有) and the resulting source hunt proved: multpl.com, aaii.com, openinsider.com, stockanalysis.com, currentmarketvaluation.com all return HTTP 200 to a normal Chrome User-Agent and parse cleanly with pandas.read_html(url, storage_options=HEADERS). Wrapping them in r.jina.ai was OVER-defense — Jina's intermittent empty returns were the actual instability, not the sites. Preferred hierarchy per indicator: (1) official pure API (FRED, CNN F&G JSON, CFTC Socrata) → (2) direct requests/read_html with a real Chrome UA → (3) Jina/web_extract only for sources that truly 403 a plain UA → (4) manual_overrides.json (cron agent web_extract) as last resort, with run.py falling back to it when its own fetch is None. When asked to find a real source / stop saying 未找到, spawn a delegate_task subagent to PROBE each candidate (akshare functions, FRED series-id search, plain-UA requests, official API gateways) and only mark 未找到 after real attempts — and offer a substitute indicator when a source is genuinely paywalled. Full verified per-indicator source map (FRED series-ids, exact URLs, parse recipes, fallbacks) lives in references/data-source-map.md.
- akshare is a China-market library — weak for US sentiment. Worth probing ([f for f in dir(ak) if kw in f]) but its buffett/pe/margin/ipo functions are all A-share口径; no US AAII/NAAIM/insider/put-call functions. Don't引入 broker APIs that need account+key (moomoo/TradingView/trading.com) when free public sources cover the 8 valuation/structural indicators — that violates Chao's no-unnecessary-credential red-line.
- web_extract > script-internal Jina remains the fallback for the FEW sources that DO 403 a plain UA (CBOE/GuruFocus/Conference-Board historically) — but always try a plain Chrome UA first now; many of the sources previously routed through Jina no longer need it.
- **CFTC COT官方 Socrata API** (`publicreporting.cftc.gov/resource/6dca-aqww.json`) is the free, no-scrape, backfillable gold/silver commercial-positioning source — prefer it over barchart (anti-scrape / partly paid). Precise-match the main contract `GOLD - COMMODITY EXCHANGE INC.` / `SILVER - …` to exclude MICRO.

- **Notion page BODY as the long-report surface.** The daily DB row's PAGE (block children) holds the rich 6-part + multi-domain content: `_clear_page_blocks` first (avoid堆积), then append heading_2/heading_3/paragraph/bulleted_list_item/callout/divider in ≤90-block PATCH batches.
